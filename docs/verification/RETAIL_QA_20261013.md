# RETAIL QA FINDINGS FIXED

Verified 13 October 2026 against a disposable localhost database ending `_test`, using separate synthetic Hardware, Clothing, Pharmacy and Footwear owners. This is a targeted QA result, not production deployment certification.

## Initial findings

| Severity | Finding | Resolution |
|---|---|---|
| HIGH | Creating a supplier from Buy Stock navigated away and discarded the purchase. | Supplier sheet stays inside the purchase and selects the saved supplier. |
| HIGH | Credit was a hardcoded frontend default with no documented product policy; an unnoticed choice could create supplier debt. | Require an explicit Paid, Credit or Partial selection; explain paid/due consequences before saving. |
| MEDIUM | “Delete” actually archived; there was no distinct protected permanent-delete flow. | Separate archive and permanent-delete actions, with server eligibility checks and strong confirmation. |
| MEDIUM | Stocked archive did not clearly explain remaining inventory. | Warn with actual quantity/unit; stock adjustment is a separate action. |
| MEDIUM | Operational stock reports hid archived inventory. | Include archived physical stock in stock reports; financial valuation already retained it. |
| MEDIUM | Oversized bill drafts showed no early stock warning. | Show available stock immediately, including selected units, dimensions and variants. |
| MEDIUM | GST pricing basis and totals were unclear. | Show exclusive price copy and server-quoted subtotal, GST and payable. |
| MEDIUM | Variant items offered no clear receiving next step. | Explain separate stock and retain item context in post-save Buy Stock. |
| LOW | Pharmacy was reported missing. | Built-in `PHARMACY` and aliases already existed; verified them, added item-category suggestions and plan-aware recommendations. |

Overselling was an uncertain finding, not an established accounting defect. The final posting tests confirmed that the existing inventory engine rejects insufficient stock and handles concurrent sales. No stock engine or tax/accounting calculation was replaced.

# PURCHASE PAYMENT

Current default discovered: the frontend initialized `status` to `CREDIT`. No separate product policy requiring that default was found; the backend already requires a valid payment status.

Final chosen behavior: no selected payment status. The user must choose Paid, Credit or Partial. Saving is disabled until chosen; invalid partial amounts are blocked.

Paid/Credit/Partial consequences clear: **PASS**. Tests verified purchases of ₹100 produce due ₹0 / ₹100 / ₹60 with ₹40 paid. Combined supplier due was ₹160. Payment method does not infer status. Existing posting/accounting rules remain unchanged.

## Scope and remaining limits

- The existing generic adjustment API cannot identify individual variants, batches or serials. The new shortcut blocks those tracked items instead of guessing which stock to alter. Extending tracked adjustment documents/API is separate work; no universal tracked write-off support is claimed.
- No 30-day sales dataset was generated. All automated writes and browser purchases used disposable test accounts/database/private upload storage. Operator credentials and customer data were preserved.
- No tax, weighted-average costing, COGS, return costing, Galla or Khata posting logic changed. Operational stock reporting now includes archived physical inventory; selling/low-stock suggestions still respect active/available stock.
- Netlify/Render/Neon deployment, real Google Cloud origins, SMTP, backup recovery and hosted acceptance remain pending. Follow [the website and cloud setup guide](../APNAGALLA_WEBSITE_AND_CLOUD_SETUP.md); this report does not declare production ready.
